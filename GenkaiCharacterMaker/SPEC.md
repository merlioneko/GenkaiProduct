# GenkaiCharacterMaker 設計案

## 1. 文書の位置付け

ユーザー構想に基づく初期版の設計案。第2節は指定された要件。基本項目に加えて自由項目を構造化して保持し、追加・編集・個別生成と外部出力を扱う方針は、2026-10-31のユーザー指示に基づき本設計へ採用する。その後の実装依頼に基づき、Python 3.12・PySide6・Pydantic 2と本書の初期版設計を採用して実装する。受け入れ条件の達成状況と実機未確認事項は実装とは区別して記録する。進行状況と検証記録は [MILESTONES.md](MILESTONES.md) に分離する。

## 2. 指定された要件

- 名前は **GenkaiCharacterMaker**。GenkaiProduct直下に独立ディレクトリを置く。
- 個人利用のローカルアプリ。主要操作はGUIで完結する。
- OpenAI互換APIでLM Studioやllama-serverへ接続する。
- 自由文の人物イメージを尊重し、性格・容姿・口調・背景などを補完する。
- 項目別の編集と再生成を行い、再生成の対象外の設定を勝手に変更しない。
- 基本項目に加え、「特殊能力」「所属組織」などの自由項目をユーザーが追加・削除・改名・並べ替えできる。各項目は項目名と複数行の本文を持ち、個別に生成・再生成できる。
- 自由項目は本アプリのJSONで構造を保持する。全体生成では登録済み自由項目の本文も候補に含め、LLMによる項目の追加・削除・改名・並べ替えは行わない。
- JSONで保存・再読込し、Markdownとして外部利用できる。
- GenkaiNovelWriterの `name`、`persona`、`appearance`、`speech_examples`、`notes` との将来の互換性を考慮する。
- **GenkaiNovelWriterの既存コード・スキーマは変更しない。** インポート機能は将来の別作業とする。
- 初期対象外：人物間の関係管理、世界・シナリオ生成、直接連携、複雑な矛盾検証、複数LLM、画像生成。
- 自由項目の数値型・選択肢型・入れ子構造・作品別テンプレートは初期対象外。所属や人間関係について自由項目に文章を書くことは可能だが、人物間リンクや世界設定の管理機能には拡張しない。
- 既存Skill・プロンプトの知見を取り込める構造にするが、Skill実行環境や拡張プラグイン機構は必須にしない。

## 3. 推奨構成と理由

**Python 3.12 + PySide6（Qt Widgets / Qt Network）+ Pydantic 2 のデスクトップアプリを推奨する。**

| 選択肢 | このアプリでの利点・負担 | 判断 |
|---|---|---|
| PySide6 / Qt Widgets | 複数行編集、ファイル選択、候補比較、設定ダイアログを一つのアプリにまとめられる。依存パッケージは大きめ | 推奨 |
| Tkinter | Python標準の範囲で小さく始められる。項目編集や候補比較を増やす場合のUI調整は多くなる | 依存サイズを最優先する場合の代案 |
| ブラウザーUI + Pythonサーバー | UI表現の自由度が高い。サーバー起動、ポート、ブラウザー、配布の管理が増える | 初期版では採用しない案 |

Pythonを選ぶ理由は既存GenkaiProductがPython中心であること、GUI以外のデータ処理を小さく保てること。NovelWriterの環境やコードを共用する必要はない。

- GUI：Qt Widgets。QML、WebView、独自描画は使わない。
- HTTP：Qt Networkの `QNetworkAccessManager` で非同期に送信する。GUIスレッドを同期HTTPや待機ループで止めない。最初からワーカースレッドやasyncioの統合は導入しない。[Qt公式資料](https://doc.qt.io/qtforpython-6/PySide6/QtNetwork/QNetworkAccessManager.html)
- 検証：Pydantic 2。保存文書・LLM応答・互換出力を別の検証境界とする。
- 保存：一人につき一つのUTF-8 JSON。データベース・ライブラリー検索画面は初期版に追加しない。
- 起動：開発時は専用仮想環境から起動。日常利用はショートカット等からGUIを起動できるようにする。インストーラー・exe化は基本動作の確認後に検討する。

## 4. 画面と操作

一つのメインウィンドウと接続設定ダイアログを基本にする。

```text
GenkaiCharacterMaker                       未保存の変更あり
[新規] [開く] [保存] [名前を付けて保存] [出力 ▼] [接続設定]
┌───────────────────┬────────────────────────────────────┐
│ 人物イメージ      │ 名前                     [再生成]   │
│                   │ 性格・価値観             [再生成]   │
│ 自由文入力        │ 容姿                     [再生成]   │
│                   │ 口調の例（台詞の一覧）   [再生成]   │
│ [全体を生成]      │ 背景・過去               [再生成]   │
│                   │ 補足                     [再生成]   │
│                   │ 自由項目                 [＋追加]   │
│                   │ 特殊能力                 [生成]     │
│                   │ 所属組織                 [再生成]   │
│                   │ 各項目：[改名] [↑↓] [削除]          │
├───────────────────┴────────────────────────────────────┤
│ 再生成時：対象「背景・過去」／修正指示                  │
│ 現在の内容                  │ 生成された候補            │
│                             │ [適用] [破棄]             │
└────────────────────────────────────────────────────────┘
接続先 / モデル / 処理状態 / エラーの要点
```

候補欄は生成時のみ表示する。編集部はスクロール可能とし、口調の例は台詞ごとに追加・編集・削除できる。改行を含む台詞も一つの配列要素として保持する。

自由項目は基本項目の下に表示する。「＋追加」で項目名を入力すると空の本文欄を追加する。追加・改名はD1の項目名検証を通してから確定する。本文は複数行テキストとして編集し、空欄からの「生成」と既存本文の「再生成」は同じ候補確認の流れを使う。項目名と本文を区別して表示し、上下移動で表示順を変える。生成前に空欄の「特殊能力」を追加しても、生成後に追加してその項目だけ作ってもよい。

1. 人物イメージを入力し「全体を生成」。現在の文書はそのまま保持する。
2. 検証できた候補を表示し、「適用」で基本項目と登録済み自由項目の本文を置換、「破棄」で元に戻る。自由項目のID・項目名・順序は置換しない。生成後すぐには保存しない。
3. 基本項目と自由項目を直接編集するか、項目の「生成／再生成」から修正指示を入力する。
4. 再生成候補の現在値・提案値を見比べ、対象項目だけを適用する。
5. JSONを保存し、必要に応じてMarkdownをファイル出力またはクリップボードへコピーする。

初期版の個別生成・再生成単位は、基本六項目の一つ、または自由項目一件の本文。複数項目選択、台詞一件だけの再生成、永続的な変更履歴は後回しにする。手編集による台詞一件の変更は可能。

生成中・候補確認中は、人物イメージと設定本文の編集、および自由項目の追加・削除・改名・並べ替えをロックする。閲覧・スクロールは可能。候補は編集せず、適用後に手編集できる。通信中は「キャンセル」を表示する。新規・開く・接続変更は処理中に開始せず、まずキャンセルまたは候補破棄を行う。終了操作は通信を中断してから未保存確認へ進む。

新規・開く・終了の前に未保存変更があれば「保存／破棄／キャンセル」。保存失敗時は元の操作に進まない。LLM未接続でも編集・保存・再読込・出力を利用できる。

## 5. 内部データと互換性

### D1. 保存文書と人物設定を分ける

正本は `CharacterDocument`。メタデータと入力文を外側、基本六項目を `character` 内へ置く。自由項目の配列 `custom_fields` は `character` と同じ文書直下に置き、基本項目と分けて保持する。

| フィールド | 型 | 意味 |
|---|---|---|
| `schema_version` | 整数、初期値1 | 保存形式の版 |
| `id` | UUID形式の文字列 | アプリが作る人物ID。LLMに決めさせない |
| `created_at` / `updated_at` | UTCのISO 8601文字列 | 作成日時／最後に本文・入力文・自由項目の定義や順序を変更した日時 |
| `idea` | 文字列 | ユーザーの人物イメージ。LLMは書き換えない |
| `character.name` | 文字列 | 名前 |
| `character.persona` | 文字列 | 性格・価値観 |
| `character.appearance` | 文字列 | 容姿 |
| `character.speech_examples` | 文字列配列 | 台詞による口調の例 |
| `character.background` | 文字列 | 背景・過去。単独で再生成するため分離 |
| `character.notes` | 文字列 | その他の補足 |
| `custom_fields` | 自由項目オブジェクトの配列 | 配列順を画面・出力の表示順とする。0件なら `[]` |
| `custom_fields[].id` | UUID形式の文字列 | アプリが発行する項目ID。同一文書内で一意 |
| `custom_fields[].label` | 文字列 | ユーザーが付ける項目名。必須・1行 |
| `custom_fields[].value` | 文字列 | 自由項目の本文。改行を含められる |

実例は [保存用JSON](examples/character.gcm.json) を参照。自由項目は固定形のオブジェクト配列として検証し、任意のJSONキーや値の型を無制限に許す方式にはしない。ユーザーによる自由項目の増減では保存形式の版を変えない。値の型など保存契約自体を変える場合に版と移行を検討する。

初期版のリリース前の設計変更のため `schema_version: 1` を維持する。自由項目のない以前の設計例も扱えるよう、版1の読込で `custom_fields` が省略された場合だけ `[]` と解釈する。新たな保存では必ず `custom_fields` を出力する。`null` や辞書を空配列へ置換する処理はしない。

自由項目の定義は次のとおりとする。

- 項目IDは追加時に発行し、改名・並べ替え・本文変更・生成適用・保存で維持する。削除後に同名の項目を追加しても新しいIDとする。画面位置や項目名を更新先の識別子にしない。
- 項目名は空文字・空白のみ・改行を含む値を拒否する。同じ文書の自由項目同士では、前後空白を除いた文字列が一致する項目名を重複として拒否する。比較以外の目的で保存文字列を自動トリミングしない。
- 本文は保存時も生成候補でも空文字・空白のみを許す。未記入や該当設定なしを表せるようにし、必要ならユーザーが「なし」「未定」と書ける。生成後も空欄ならそのまま候補として見せる。
- 各要素の許可キーは `id`・`label`・`value` の三つだけ。キー欠落、余分なキー、型違い、項目IDの重複を拒否する。自由項目自体のラベル重複も読込時に検証する。
- 追加・削除・改名・並べ替え・本文変更は文書の変更として扱い、変更があった場合にrevision・更新日時・未保存状態を更新する。削除で失われるのはそのIDの項目だけであり、他項目を詰め直してIDを付け替えない。

基本項目の下書き保存では空の文字列と空の台詞配列を許す。全体生成の成功候補は基本六項目のキーすべてを要求し、名前・性格・容姿・背景の空白のみの値を拒否する。補足は空欄でもよい。台詞は1件以上で、各要素が空白のみではないことを求める。基本項目の部分再生成では対象キーだけを必須とし、対象について全体生成と同じ非空条件を適用する。台詞数を元と同じに固定する意味ではない。自由項目には上記の空欄規則を適用する。型の暗黙変換や無断の文字列トリミングはしない。

保存文書・基本項目・自由項目とも、未知のキー、型違い、非対応の `schema_version` は読込エラーとする。`custom_fields` は定義済みの保存項目なので、この未知キー拒否の方針と両立する。未知の内容を捨てて再保存しない。重複JSONキーも拒否する。読込検証が完了するまでは、開いている文書を置き換えない。

`id` は新規作成時に発行し、再生成・保存・名前を付けて保存では維持する。「別キャラクターとして複製」は将来の別操作とする。`created_at` は維持し、変更なしの保存・出力・候補破棄では `updated_at` を更新しない。

### D2. GenkaiNovelWriter用の出力境界

確認した既存 `Character` は以下の五つのキーを持ち、`strict=True` と `extra="forbid"` を使用している。`speech_examples` は **1件以上の `list[str]`**。他の四項目は文字列であり、既存スキーマには非空文字列の制約はない。

内部の `background`、`custom_fields`、ID、版番号、入力文をそのまま渡すと既存モデルの形式に合わない。独立した純粋関数 `to_novelwriter_character(document)` で次のオブジェクトを作る。

| 出力キー | 変換規則 |
|---|---|
| `name` / `persona` / `appearance` | 同名の値をそのままコピー |
| `speech_examples` | 文字列配列を順序ごとコピー。空配列なら互換出力を止めて修正箇所を表示 |
| `notes` | 下記の固定規則で背景・補足・自由項目を統合 |

まず背景と補足を次の規則でまとめる。`background == ""` の場合、基本項目の `notes` をそのまま使う。それ以外は `"## 背景・過去\n" + background` とし、基本項目の `notes != ""` なら `"\n\n## 補足\n" + notes` を末尾に足す。

自由項目が1件以上なら、各項目を `"### " + heading(label) + "\n" + value` として配列順に `"\n\n"` で連結し、先頭に `"## 自由項目\n\n"` を付けたブロックを作る。背景・補足の結果が非空なら `"\n\n"` を挟んで追加し、空なら自由項目ブロックだけを出力する。`heading(label)` はD7の見出し用エスケープであり、本文は変換しない。自由項目0件なら自由項目の見出し自体を出さない。本文が空の項目も項目名は残す。

本文自体の要約・再生成・トリミングはしない。統合は出力時だけ行い、正本を書き換えない。五項目JSONでは自由項目の配列構造・IDは失われるが、項目名と本文は残る。構造を保つ再編集用の正本は本アプリのJSONとする。

[互換JSON例](examples/character.novelwriter.json) は一人分の五項目オブジェクトであり、`Plot` 全体やインポート機能ではない。出力メニューには「5項目JSON（将来の受け渡し用）」を用意する案とする。初期版の中心は保存用JSONとMarkdownである。

互換JSONからの逆変換は初期対象外。統合した `notes` から背景・自由項目を復元する推測処理は作らない。実行時にNovelWriterをimportせず、共通ライブラリー化も行わない。

## 6. 生成・部分再生成

### D3. モデルが変更できる範囲をアプリで制限する

全体生成の応答は、基本六項目のオブジェクト `character` と、自由項目の候補配列 `custom_values` の二つのキーだけを持たせる。`custom_values` の各要素は `id` と文字列の `value` だけとし、既存項目のIDを照合に使う。文書メタデータや項目名は応答に含めない。

全体生成の要求には、現在の基本項目、入力文、および自由項目のID・項目名・現在値を送る。応答の自由項目ID集合と件数が要求時点の一覧に一致することを検証し、未知ID・重複ID・不足・余分なキーを拒否する。自由項目が0件なら応答も `custom_values: []` とする。返却された配列順は採用せず、アプリが元の順序で各IDの本文だけを候補に組み込む。基本項目と自由項目の両方の検証が通ってから一つの全体候補を提示し、片方だけの適用はしない。

個別生成・再生成には現在の基本六項目と自由項目、人物イメージ、対象、今回の指示を渡す。基本項目の例として背景だけなら応答形式は次に限定する。

```json
{"background": "新しい背景・過去の設定"}
```

自由項目一件の場合、対象IDと項目名をアプリ側で固定し、応答は次の形式に限定する。ID・項目名・配列位置をLLMに返させて更新先を決めることはしない。

```json
{"value": "触れた物体の記憶を読み取れる。ただし、読み取れるのは直近の一場面だけ。"}
```

1. アプリ側で対象を、基本六項目の許可リストまたは現在の自由項目のID一覧から選ぶ。基本項目名と自由項目IDは種類を分けて管理し、LLMに対象を決めさせない。
2. 要求開始時の文書セッションID・本文revision・要求ID・対象を保存する。
3. 応答をJSONとして読み、基本項目ならキー集合が `{対象フィールド}`、自由項目なら `{"value"}` と完全一致し、値の型・対象の制約に合うか検証する。
4. 余分なキーがある応答はエラーとし、一部だけ拾って成功扱いにしない。
5. 検証成功後も候補として保持し、ユーザーの「適用」までは正本を変更しない。
6. 適用時も要求の有効性と対象の存在を確認し、元の文書をコピーして **基本項目の対象キー、または指定IDの自由項目の `value` だけ** を更新する。自由項目配列全体をLLMの応答で置換しない。
7. 人物イメージ、人物ID、作成日時、対象外の設定、自由項目のID・項目名・順序は維持する。値が変わった場合のみrevisionと更新日時、未保存状態を更新する。

これにより、例えば特殊能力の再生成で性格・容姿・台詞・所属組織が書き換わらないことはコードで保証できる。新しい本文が他の設定と意味的に矛盾しないことは別問題で、初期版ではプロンプトと候補確認で扱う。複雑な自動矛盾検証は追加しない。

### D4. 応答・キャンセル・エラー

状態は `編集可能 → 通信中 → 候補確認 → 編集可能`。エラーまたはキャンセルは現在の正本を保って編集可能へ戻す。同時の生成要求は一件とする。

文書セッションIDは新規・開くごとに新しく発行する実行時の値とし、保存IDとは分ける。同じ人物ファイルの開き直しでも過去の応答を受け入れない。revisionは自由項目の構成・項目名・順序の変更も含めて管理し、要求開始時と異なれば候補を適用しない。削除済みIDへの遅延応答で項目を復活させたり、同名の新しい項目へ適用したりしない。revision・要求IDも実行時に管理し、保存データへ混入させない。

キャンセルは先に要求IDを無効化してから `QNetworkReply.abort()` を呼ぶ。応答の `errorOccurred` / `finished` の重複通知を一回の終端処理にまとめ、タイマーを停止してreplyを `deleteLater()` で解放する。タイマーも要求IDに関連付け、発火時にその要求が有効か確認する。キャンセルに伴うエラーは通信故障の表示にしない。古い完了通知が、新しい処理のロックや状態を解除することも防ぐ。[Qt QNetworkReply](https://doc.qt.io/qtforpython-6/PySide6/QtNetwork/QNetworkReply.html)

中断でサーバー側の推論停止まで保証できるとは扱わない。アプリ側は中断した結果を採用しない。タイムアウトにも同じ経路を使う。

APIの外側の応答JSONと、`choices[0].message.content` 内の設定JSONを別々に検証する。空応答・HTTPエラー・不正JSON・型不一致・想定外キー・途中切れは正本に適用しない。`finish_reason == "length"` はJSONが読めても不完全候補として拒否する。通常の `stop` 以外の終了理由は理由を表示し、無条件に成功扱いしない。

応答全体が単一のJSONコードフェンスの場合だけ、その外枠の除去を許す案とする。任意の説明文から括弧を探してJSONを推測抽出したり、LLMへ自動修復を連鎖させたりしない。詳細表示と、ユーザー操作による再試行を提供する。

### D5. プロンプト

`prompts/generate.md` と `prompts/regenerate.md` を通常のUTF-8テキストとして持つ。初期版ではアプリ同梱の固定パスから読む。任意のSkill実行・コード実行は実装しない。

- 初回生成：入力で明示された要素を保ち、不足部分だけを補完する。指定された弱点や矛盾した性格を無断で「改善」しない。
- 全体生成：自由項目はユーザーが登録した分だけを扱い、その項目名・人物イメージ・現在値に沿って本文を提案する。登録のない特殊能力などを独立項目として追加しない。項目の追加・削除・改名・並べ替えは生成指示の対象外とする。
- 部分再生成：今回の指示は選んだ項目にだけ適用する。原案の変更を明示された場合はその範囲で扱い、対象外への変更を要求する指示は対象を広げて実行しない。
- 他項目は参照用の確定値として渡す。追加の人間関係表、世界設定、シナリオを生成しない。
- ユーザー文・設定本文はJSONシリアライズしたデータとして区切り、固定の出力契約と分離する。
- 自由項目の項目名もデータとして渡す。項目名や本文に出力形式変更などの指示が書かれていても、アプリの出力契約や適用先を変更しない。
- APIの構造化出力を使う場合も、必要なキー・型をプロンプトへ明示し、アプリ側で再検証する。

既存キャラクター作成Skillを入手できた場合は、その創作方針や項目の説明をこの二つのプロンプトへ整理する。Skillの全文コピーやOpenWebUI依存を前提条件にしない。

## 7. LLM接続設定

LM Studioとllama-serverに共通する `GET /v1/models`、`POST /v1/chat/completions` を基本にし、`stream: false` とする。生成の進捗は経過時間と処理中表示で示し、推測の進捗率を出さない。[LM Studio互換API](https://lmstudio.ai/docs/developer/openai-compat)

設定ダイアログに以下をまとめる。

| 設定 | 初期案 |
|---|---|
| 接続先 | `http://127.0.0.1:8080/v1`。指定されたllama-serverに合わせた初期値。LM Studioの例は `http://127.0.0.1:1234/v1` |
| モデル | 一覧を取得して選択。モデルIDの手入力も可能。自動的に先頭モデルへ切り替えない |
| 認証 | 未設定ならAuthorizationを付けない。必要な場合はセッション中だけ入力値を保持する案 |
| temperature | 初期案0.7 |
| max_tokens | 8192。推論だけで2048を消費した実測に基づき変更。途中切れ時に増やせる |
| 要求の期限 | 300秒。推論モデル向けに調整。送信から完了までをタイマーで測り、到達時はabortする |
| 出力モード | 初期実装は通常JSON指示に固定。構造化JSONは生成安定性に課題が出た場合の追加候補 |

通常JSON指示では `response_format` を送らない。まず両サーバーでこの方式を実装・評価し、初期版の完成に構造化出力の実装を要求しない。必要になった場合は、LM Studioの `response_format.json_schema` とllama-serverの対応バージョンの形式を小さな分岐で組み立てる。プラグイン式のバックエンド抽象化は導入しない。実機で形式を検証するまで対応済みとは扱わない。[LM Studio構造化出力](https://lmstudio.ai/docs/developer/openai-compat/structured-output)、[llama-server API資料](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md)

構造化出力を追加する場合だけ設定にモード選択を設け、拒否された場合は原因を示して通常モードへ戻せるようにする。全HTTPエラーを理由に自動再送するフォールバックは設けない。モデル一覧の取得成功は接続確認であり、生成成功・構造化出力対応の証明とは区別する。

設定は本アプリ専用のローカル設定領域へ保存する。キャラクターJSON、Markdown、ログへ認証値を含めない。クラウドへの自動切替・モデル自動ダウンロード・サーバー自動起動は行わない。LM Studio等の起動とモデルロードは既存の推論環境側で行う。

## 8. 保存とMarkdown出力

### D6. 保存

- 既定の保存先はプロジェクト内の `creations/characters/`。GUIから任意の保存先を選べる。
- ファイル名案は `<id>.gcm.json`。人物名からパスを自動生成せず、日本語名や同名キャラクターを扱えるようにする。
- UTF-8、インデント2、`ensure_ascii=False`。同一フォルダーの一時ファイルへ書いて成功後に置換する。
- Qtの `QSaveFile` を利用し、直接上書きのフォールバックは有効にしない。書込・commitの成否を確認し、成功後だけ未保存表示を解除する。[QSaveFile公式資料](https://doc.qt.io/qtforpython-6/PySide6/QtCore/QSaveFile.html)
- 読取専用・ディスク不足・置換失敗では編集中の文書を保持し、別名保存を案内する。原子的置換が利用できない保存先では保存失敗として扱う。
- JSON読込失敗時も現在の文書と未保存状態を保持する。自動保存・クラッシュ復旧・複数アプリからの同時編集は初期対象外。

### D7. Markdown

順序を「名前 → 性格・価値観 → 容姿 → 口調の例 → 背景・過去 → 補足 → 自由項目」に固定する。自由項目がある場合は `## 自由項目` の下に `### 項目名` と本文を配列順で出力する。自由項目0件ならこの節を出さず、本文が空の項目も項目名は残す。LLMを呼ばず、現在の設定から決定的に生成する。台詞は配列順の箇条書きとし、台詞内の改行を継続行として表現する。

名前中の改行は見出し用の表示で空白に置換し、名前・自由項目名に含まれるMarkdown記号は出力時だけエスケープする。具体的にはバックスラッシュを先に二重化し、見出し中の `` ` * _ { } [ ] ( ) # + - . ! | ~ `` をバックスラッシュでエスケープ、`&`・`<`・`>` をHTMLエンティティにする。自由項目名はD1で改行を拒否する。本文にはこの見出し変換を適用せず、正本の文字列は変更しない。

空欄の下書きも出力可能とする。名前未設定なら見出しを「未命名」とし、それ以外の空欄には内容を補わない。入力文・ID・接続設定・候補を通常のMarkdownへ混ぜない。[出力例](examples/character.md) を基準にする。

ファイル出力とクリップボードコピーは同じ文字列を使う。保存前の編集内容も出力できるが、出力で正本の未保存状態は解除しない。保存用JSONと同一パスへのMarkdown・互換JSON出力は拒否する。

## 9. モジュール構成案

以下の構成で初期実装する。起動用にstart.batと初回環境構築用にsetup.batも配置する。

```text
GenkaiProduct/
├─ GenkaiNovelWriter/
├─ GenkaiIllustrator/
└─ GenkaiCharacterMaker/
   ├─ README.md / SPEC.md / MILESTONES.md
   ├─ requirements.txt
   ├─ main.py
   ├─ character_maker/
   │  ├─ models.py       # 保存形式と応答の型。GUI・HTTP・ファイルI/Oに依存しない
   │  ├─ generation.py   # プロンプト構築・応答検証・対象限定の適用
   │  ├─ gateway.py      # Qt NetworkでHTTP。応答本文と失敗を通知
   │  ├─ storage.py      # 検証後の読込・原子的な保存
   │  ├─ exporters.py    # Markdownと五項目JSONの純粋変換
   │  ├─ settings.py     # 本アプリの接続設定
   │  └─ ui/
   │     ├─ main_window.py
   │     └─ settings_dialog.py
   ├─ prompts/
   │  ├─ generate.md
   │  └─ regenerate.md
   ├─ test/
   ├─ examples/
   └─ creations/characters/   # 利用者の保存データ。既存のcreations除外規則の対象
```

小規模な明示的な関数・クラスで始める。DIコンテナー、イベントバス、汎用リポジトリー層、共通Product SDKは導入しない。ネットワーク要求の状態は一か所で持ち、UIから純粋な検証・変換関数を呼べるようにする。

## 10. 受け入れ条件案

ユーザー指定要件の成立を確認するための提案。実装の進捗・検証結果はMILESTONESでこのIDを参照する。

| ID | 条件 |
|---|---|
| AC-01 | GUIだけで人物イメージ入力→生成候補確認→適用→手編集→保存→再読込→Markdown出力が完結する |
| AC-02 | 基本六項目と自由項目各一件を単独生成・再生成でき、適用後の対象外設定・入力文・人物ID・作成日時、および自由項目のID・項目名・順序が適用前と完全一致する |
| AC-03 | 候補破棄・通信失敗・不正JSON・余分なキー・型違い・途中切れで正本が変わらない |
| AC-04 | キャンセル後や文書切替後、自由項目の削除・改名・並べ替え後の遅い応答が、別要求の候補・文書・UI状態に作用せず、同名で新規追加された項目へも適用されない |
| AC-05 | JSON保存→再読込で日本語・改行・台詞の順序・背景・メタデータと自由項目のID・項目名・本文・順序を維持し、空欄の下書きも保持する。版1でcustom_fields省略なら空配列として読み、以後の保存には出力する |
| AC-06 | 保存失敗・不正ファイル・未知の版やキー・自由項目の重複IDや重複ラベル・不正な型で現在の文書を失わず、未保存確認で保存を選び失敗した場合に切替・終了しない |
| AC-07 | Markdownに自由項目の項目名・本文が表示順に含まれ、空本文の項目名も残る。ファイルとコピー内容が一致し、出力で正本・未保存状態が変わらない |
| AC-08 | 五項目JSONが確認済みCharacterのキー・型・台詞最低件数に一致し、背景・補足・自由項目をD2の規則でnotesへ反映する。空台詞配列は出力を止める。自由項目0件・空本文・背景と補足の空欄の組合せも扱う |
| AC-09 | LM Studioとllama-serverの各一環境で、接続・全体生成・項目再生成を実測する。通常JSONモードを必須とし、構造化モードを追加した場合の結果は別記する |
| AC-10 | LLM未接続でも手編集・保存・読込・出力ができ、推論中にウィンドウが応答し、キャンセルできる |
| AC-11 | 例の「明るく人懐っこい魔女／自分の命にはほとんど執着がない」の両要素が生成候補で保たれ、背景変更後も性格の値が変わらない。意味の保持は人が確認する |
| AC-12 | GenkaiNovelWriterのコード・スキーマ・設定を変更せず、同プロジェクトの実行環境がなくても起動する |
| AC-13 | GUIで自由項目を追加・削除・改名・並べ替え・手編集できる。改名・並べ替えでIDを維持し、項目名の空欄・改行・重複を拒否する。変更を未保存状態へ反映し、生成中・候補確認中は項目操作もロックする |
| AC-14 | 全体生成で登録済み自由項目の本文を候補化し、ID・項目名・順序を保持する。未知ID・重複ID・不足・余分なキーの応答は全体を拒否し、0件の場合も項目を増やさない |

自動テストは基本項目・自由項目の対象限定更新、全体候補のID照合、古い要求の排除、厳密な型検証、保存失敗時の保持、自由項目を含む往復保存、互換変換を重点にする。GUIの項目操作とローカルモデルでの日本語品質は別途確認する。大量の成功回数だけで創作品質を合格扱いにしない。
