# GenkaiNovelWriter 仕様書

## 概要

### 目的

手動で効果を確認済みのワークフロー「設定・プロットを壁打ち → 同じ文脈でシーンごとに執筆」を自動化し、ローカルLLMで満足できる品質の短編小説を得る。

手動運用には次の課題があり、本プロジェクトはこれを解消する。

| 手動運用の課題 | 対応する設計要素 |
|---|---|
| フェーズごとにシステムプロンプトを入れ替える手間 | フェーズの自動遷移(CLI) |
| 設定を別の会話に移行しにくい | ファイルとして保存される中間成果物(Concept / Plot) |
| 長コンテキスト対応モデルが必要 | 1回の生成に渡す情報を、そのフェーズに必要な分に限定する |

一発生成で生じる次の問題の低減も狙う。

- 曖昧な入力に対して、ありきたりな作品になる(当面は改善区分。後述)
- ありえない身体動作など、物理的な破綻が生じる

### 実行環境・技術スタック

| 項目 | 内容 |
|---|---|
| 言語 | Python |
| 推論ランタイム | LM Studio(OpenAI互換API) |
| 実行マシン | デスクトップ(Ryzen 7 9800X3D / RX 9070 XT 16GB / RAM 64GB) |
| 構造化・検査モデル | Qwen3.6-35B-A3B(Q4基準) |
| 執筆モデル | Gemma 4 26B-A4B(Q4基準) |
| コンテキスト長 | 16384以上 |
| 補助バックエンド | OpenRouter(動作確認専用) |
| インターフェース | CLIのみ |

## 確定事項

### 目的・範囲

| ID | 決定 | 理由 |
|---|---|---|
| D1 | 本番・品質評価はローカルLLMでのみ行う | 元の動機がローカル生成であり、パイプラインは弱いモデルを補う手段として設計されているため |
| D2 | OpenRouterは動作確認・デバッグ専用とし、その結果を品質評価に使わない | モデルも量子化もローカルと異なり、品質判断を持ち込めないため |
| D3 | 出力は1話完結の短編。総字数4000〜5000字、1シーン1000字前後を目安とする | 読みたい量として決定。字数は目安であり、合否には使わない |
| D4 | 余韻としての未回収伏線は許容する | 禁止すると、無理に回収させた不自然な展開を招くと判断したため |
| D5 | 当面はCLIで実装し、UIは作らない | 前身プロジェクト(Sitaigeri)で、UIとパイプラインを同時に作って方向を見失ったため |

### パイプライン

| ID | 決定 | 理由 |
|---|---|---|
| D6 | Concept → Structure → Writing → Check の4フェーズ構成とする | 計画(設定・プロット)と執筆の分離は、手動運用で効果を確認済みのため |
| D7 | 旧「Joining(結合処理)」フェーズは廃止し、Check(検査)フェーズに置き換える | 境界の矛盾は、生成後に直すのではなく、生成時に前シーンの本文を渡して防ぐ(D10)方針にしたため |
| D8 | Conceptの権限は「補完のみ」とする。ユーザ指定の要素・順序・ジャンルは変更しない | 旧実装で、Conceptが展開の順序とトーンを書き換え、後段がすべてずれた前提で動いたため |
| D9 | Conceptの出力は「指定要素(ユーザ入力由来・変更不可)」と「補完要素」を区別して記述する | 指定要素の欠落や改変を、機械的・人手の双方で照合できるようにするため |
| D10 | 執筆はシーン単位で行い、既に書いたシーンの全文を文脈に含める(B'方式) | 手動運用では、前シーンが同じ会話内に残った状態で書いていたため。旧実装の境界矛盾(家・天候・場所)はこれがないことが原因だったため |
| D11 | Writingには指定要素リストを直接渡す | 旧実装では、Writingがユーザ意図を要約経由でしか知らず、要素が欠落したため |
| D12 | ユーザの明示指示(必ず回収すべき伏線などを含む)は、すべて指定要素に集約する | 同じ役割を持つタグ機構を別に作らないため |
| D13 | Plot確定時点で未決定事項(「または」「例」など)を残さない | 旧実装で、Conceptの「(または〜)」が、両案とも本文に書かれたため |
| D14 | 当該話で使わない登場人物・設定をPlotに含めない | コンテキストの浪費と、無関係な設定の誤用(神社跡地の要素が自宅描写に混入)を防ぐため |
| D15 | Plotにジャンル・トーン・文体・視点の欄を設ける | 旧実装で、Writingがジャンルを知る手段がなく、ドタバタラブコメがシリアスになったため |
| D16 | シーンは順序付きのビート(必ず起こす出来事)と開始時点の状態(場所・時間帯・天候)で表現する | 旧実装で、summaryの文言が本文に流用され、出来事の順序も落ちたため |

### 検査

| ID | 決定 | 理由 |
|---|---|---|
| D17 | 検査は全シーン執筆後に一括で行う | シーンごとに検査すると、モデル切り替えがシーン数×2回発生するため |
| D18 | 検査結果は報告のみとし、自動再生成はしない | 再生成で直る保証がなく、ループの停止条件も定まらないため。手動運用の「目に余る場合のみ指示を追加」を人手による再開で再現する |
| D19 | LLMによる検査は、項目ごとに別の呼び出しにする | 1回の呼び出しに項目を詰め込むと、注意が分散して見落としが増えるため |
| D20 | 機械的に判定できる項目(字数、英字混入、メタ語、思考タグ)はLLMを使わず判定する | 確実かつ安価に判定できるため |

### 実行・データ

| ID | 決定 | 理由 |
|---|---|---|
| D21 | 各フェーズは、前段の成果物ファイルを読み、自分の成果物をファイルに書く | ステージ単体実行・手動編集・途中再開を、フルスクラッチと同じ仕組みで実現するため |
| D22 | 実行単位は「フルスクラッチ」「ステージ単体」「シーンkからの再開」の3種類とする | 将来のUI構想(一括ボタン・ステージ別ボタン・再生成)に必要な操作を、CLIで先に実現しておくため |
| D23 | 上流の成果物を再生成した場合、下流の成果物は削除せず退避する | 再生成前後の比較が評価作業の一部であるため |
| D24 | 成果物のパースに失敗した場合は、LLMで修復せずエラーとして停止する | 手動編集した成果物の誤りを、黙って書き換えないため |

### 実装基盤

| ID | 決定 | 理由 |
|---|---|---|
| D25 | LLM接続はOpenAI互換クライアントの1クラスに統一し、接続先は設定ファイルで切り替える | LM StudioとOpenRouterの差は base_url・api_key・model だけのため |
| D26 | フェーズごとに、使用モデル・思考モードの有無を設定ファイルで指定する | モデル割り当てが仮決定(U6)であり、コードを変えずに差し替えるため |
| D27 | 2モデルは同時にロードせず、フェーズ順に1モデルずつ切り替える | パイプラインは逐次処理であり、同時ロードはVRAMの取り合いで速度を落とす可能性があるため |
| D28 | 必須経路(main → フェーズ → gateway)は、範囲外の機能(Tavily検索など)に依存しない | 旧実装で、gatewayがTavilyをimportしており、検索キーがないと起動しなかったため |
| D29 | すべてのLLM呼び出しについて、トークン使用量と所要時間をログに記録する | コンテキスト見積もり(U5)と速度評価(U7)を実測で確定するため |

## 未確定事項

| ID | 未確定の内容 | 確定に必要な検証 | ゲート |
|---|---|---|---|
| U1 | パイプラインが一発生成より良い結果を出すか | 同一モデル・同一入力で、ベースライン(一発生成)とパイプラインの出力を比較し、評価表に記録する | M5完了まで。これが否定された場合は、目的に対する手段を再検討する |
| U2 | LM StudioのAPI経由で、思考モードをリクエスト単位で切り替えられるか。思考内容が `content` から分離されるか | Qwen・Gemmaの両方で、切り替え手段(リクエストパラメータ、テンプレート設定など)を実機で確認する | M1完了まで。M3(執筆で思考オフ)の着手条件 |
| U3 | Qwen3.6 + LM Studio で、JSON Schema指定の構造化出力が安定して動くか | 本仕様のPlotスキーマで10回生成し、スキーマ違反の件数を記録する | M1完了まで。M2の着手条件 |
| U4 | LM StudioのJITロードで、フェーズ間のモデル切り替えが自動で行われ、前のモデルが解放されるか | 2モデルを交互に指定して呼び出し、ロード状態とメモリ使用量を確認する。不可なら `lms` CLIで明示的に切り替える方式に変える | M1完了まで |
| U5 | コンテキスト長16384で、最終シーンの執筆が収まるか | M3で実行時のトークン使用量ログ(D29)を確認する | M3完了まで |
| U6 | 検査をQwenに担当させる割り当てが妥当か | 正解付きフィクスチャ(旧実装のNemotron出力と、既知の問題一覧)で、検出率・誤検出数を測る。同じデータでGemmaにも検査させて比較する | M4完了まで |
| U7 | Q4 + エキスパートCPUオフロードで、許容できる速度が出るか。許容速度の基準自体も未定 | M1で各モデルの生成速度(tok/s)を計測し、M5でフルスクラッチ1回の所要時間を計測する。基準はユーザが実測値を見て決める | M5完了まで |
| U8 | 成功基準の具体的な閾値 | 下記「成功基準」の案を、M5の評価結果を見て確定する | M5完了まで |

### 成功基準(案)

| 項目 | 判定方法 | 基準(案) | 区分 |
|---|---|---|---|
| 要素保持 | 指定要素がすべて本文に含まれ、順序が守られているか | 欠落・順序違反0 | 合否 |
| ジャンル・トーン適合 | 指定されたジャンル・トーンで書かれているか | 人手で適合と判定できる | 合否 |
| 設定一貫性 | 口調・外見・場所・天候などが、Plotおよびシーン間で矛盾しないか | 矛盾0 | 合否 |
| 物理的妥当性 | 身体動作・位置関係に破綻がないか | 通読で気づく破綻0 | 合否 |
| 字数 | シーンごとの字数 | 600字未満のシーンがあれば警告 | 警告のみ |
| 伏線放置 | 本文内で重く扱われたのに、以降触れられない要素 | 件数を記録する | 観察のみ |
| 非陳腐性 | 曖昧入力で、ベースラインと比較して人手で判定 | 記録のみ | 改善区分(当面は合否に使わない) |

未回収伏線の判定は、次の区別に従う。

| 区分 | 定義 | 扱い |
|---|---|---|
| 余韻としての伏線 | 本文中の事実と衝突せず、答えが示されていないだけ | 許容 |
| 設定矛盾 | 本文中の既出の事実、またはPlotと衝突する | 失敗 |
| 放置 | 重く扱われたのに、以降一切触れられない | 観察項目 |

## 受容したトレードオフ

| 捨てた選択肢 | 理由 |
|---|---|
| Conceptによる展開の再解釈(陳腐さ対策) | 意図の破壊を防ぐことを優先した。陳腐さへの対策は当面行わない |
| 改変許容度の可変化 | ユーザ入力の具体度との兼ね合いが定まるまで保留。許容度の記述はプロンプト内の1箇所にまとめ、将来パラメータ化できる形にだけしておく |
| シーンの独立再生成 | B'方式により、シーンkは1〜k-1の本文に依存する。シーンkを変えたらk+1以降も再生成する |
| 自動修正ループ | 検査は報告のみ。修正は人手で再開コマンドを実行する |
| 手動壁打ちの会話文脈そのものの引き継ぎ | 設定移行の問題を解くため、壁打ち相当の内容をConcept/Plotに圧縮する。手動との品質差が出た場合の原因候補として記録しておく |
| 2モデルの同時ロード | 切り替え時のロード時間を受け入れ、VRAMの取り合いを避ける |
| 字数の厳密な制御 | 上限超過に品質上の実害はほぼないため、下限警告のみとする |
| 連載対応 | 範囲外。ただし作品レベル(登場人物・設定)と話レベル(シーン)はスキーマ上で分けておく |
| UI | 範囲外 |
| Tavily検索、GenkaiIllustrator連携 | 範囲外。コードは残してよいが、必須経路からは参照しない |

## アーキテクチャ

### データフロー

```
00_input.txt
   │  [Concept]   Qwen   補完のみ。指定要素/補完要素を区別
   ▼
02_concept.md ──[Concept照合] Qwen → 02_concept_report.json(報告のみ)
   │  [Structure] Qwen   JSON Schema制約付き生成
   ▼
03_plot.json ──[Plot機械検査] → 03_plot_report.json(報告のみ)
   │  [Writing]   Gemma  シーン1から順に。既存シーン全文を文脈に含める
   ▼
04_scenes/scene_01.md ... scene_NN.md
   │  [Assemble]  LLMなし  結合・字数集計
   ▼
05_draft.md
   │  [Check]     機械検査 + Qwen(項目別に呼び出し)
   ▼
06_check/*.json, 06_check_report.md
```

モデルのロード順は、Qwen → Gemma → Qwen の2回切り替えとなる。

### 02_concept.md フォーマット

見出しは固定とし、パーサはこの見出しで分割する。

```markdown
# 指定要素
- [S1] ジャンル: ドタバタラブコメ
- [S2] 魔人は何らかの理由でギャルの家に住み着いている
- [S3] 友人が他校の生徒に傷つけられ、ギャルがカチコミに行くのを魔人が見送る
...

# 補完要素
## 世界設定
## 登場人物
## 展開
```

規則は次のとおり。

- **指定要素**: ユーザ入力に明示された要素・順序・ジャンルを、入力の順に列挙する。IDは `S` + 連番とする。
- **補完要素**: 指定要素と矛盾しない範囲で空白を埋める。指定語を具体化する場合、語の意味を弱めない(例: 「最悪の魔人」の「最悪」を失わせない)。
- **新規の登場人物・出来事**: 指定要素の成立に必要な範囲に限る。
- **未決定の選択肢**: 「または」「例」の形で出力しない。

### 03_plot.json スキーマ

```python
class Meta(BaseModel):
    genre: str            # 例: ドタバタラブコメ
    tone: str             # 例: 軽快、ツッコミ多め、終盤のみ熱い
    style: str            # 文体の指定(例: 地の文は三人称、会話多め)
    pov: str              # 視点人物

class SpecifiedElement(BaseModel):
    id: str               # "S1" 形式。02_concept.md と一致させる
    text: str

class Character(BaseModel):
    name: str
    persona: str
    appearance: str
    speech_examples: list[str]   # 1件以上
    notes: str

class Setting(BaseModel):
    name: str
    kind: Literal["place", "worldrule", "item"]
    notes: str

class SceneState(BaseModel):
    place: str            # Settings のうち kind="place" の name と一致すること
    time_of_day: str
    weather: str

class Scene(BaseModel):
    name: str
    opening: SceneState
    beats: list[str]      # 1件以上。順序どおりに起こす出来事。本文ではなく指示
    covers: list[str]     # このシーンで満たす指定要素のID
    target_chars: int     # 目安字数。既定1000

class Plot(BaseModel):
    meta: Meta
    specified_elements: list[SpecifiedElement]
    characters: list[Character]   # 1件以上。作品レベル
    settings: list[Setting]       # 1件以上。作品レベル
    scenes: list[Scene]           # 1件以上。話レベル
```

全モデルで `extra="forbid"` とする。旧スキーマ(先頭大文字のキー)との互換性は持たせない。

## ビジネスロジック

### Concept

- **入力**: `00_input.txt`、`prompts/concept/system.md`
- **出力**: `02_concept.md`
- **照合(Concept照合)**: `00_input.txt` と `02_concept.md` の指定要素をQwenで比較し、欠落・順序変更・意味の弱化を `02_concept_report.json` に出力する。報告のみで、処理は止めない。
- 改変許容度の指示文は `concept/system.md` 内の1箇所にまとめる(将来のパラメータ化に備えるため)。

### Structure

- **入力**: `02_concept.md`、`prompts/structure/system.md`
- **出力**: `03_plot.json`(JSON Schema制約付き生成)
- **リトライ**: スキーマ違反の場合は最大2回再生成する。すべて失敗した場合は、生の出力を `03_plot_raw.txt` に保存して停止する。
- **指定要素**: `specified_elements` は、`02_concept.md` の指定要素をそのまま転記する(LLMに書き直させない)。パーサで抽出し、生成結果に上書きする。

### Plot機械検査

LLMを使わず、次を検査して `03_plot_report.json` に出力する。報告のみで、処理は止めない。

| 検査 | 内容 | 対応 |
|---|---|---|
| 未決定表現 | 全文字列フィールドに「または」「(例)」「例:」などを含む | D13 |
| 未使用要素 | どのシーンの `beats` にも名前が現れない登場人物・設定 | D14 |
| 場所参照 | `opening.place` が `settings` の `kind="place"` に存在しない | 旧実装の「自宅が未定義」問題 |
| 指定要素の未割当 | どのシーンの `covers` にも含まれない指定要素ID | 要素保持 |

### Writing

シーンkの入力は、次の順に組み立てる。

1. `prompts/writing/system.md`
2. `meta`(ジャンル・トーン・文体・視点)
3. 指定要素リスト
4. 登場人物・設定
5. 全シーンの一覧(名前とビート)。担当シーンを明示する
6. シーン1〜k-1の本文(`04_scenes/` から読む)
7. 担当シーンの `opening`・`beats`・`target_chars`

規則は次のとおり。

- **出力**: 担当シーンの本文のみ。見出し・メタ文・注記は書かない。
- **ビートの扱い**: 本文に書き写す対象ではなく、起こす出来事の指示として扱う。
- **思考モード**: オフ(設定で変更可能)。
- **再開**: `--from k` の場合、シーン1〜k-1は既存ファイルをそのまま使う(手動編集を反映するため)。
- **コンテキスト超過**: APIがエラーを返した場合は停止し、その時点のトークン使用量をログに出す。自動で入力を切り詰めない。

### Assemble

- シーンを順に結合して `05_draft.md` を出力する。
- シーンごとの字数(空白・改行を除く)を集計し、600字未満のシーンを警告する。

### Check

| 項目 | 方式 | 内容 |
|---|---|---|
| contamination | 機械 | 英字の混入(固有名として許可したものを除く)、メタ語(「Episode」「第1話」「幕を閉じた」など)、思考タグ(`<think>` など) |
| length | 機械 | Assembleの字数集計 |
| elements | Qwen | 指定要素が本文に含まれ、順序が守られているか |
| consistency | Qwen | 口調・外見・場所・天候・時間帯について、Plotおよびシーン間で矛盾していないか |
| physical | Qwen | 身体動作・位置関係・物の性質(打撃武器が刺さるなど)の破綻 |

- LLM検査は項目ごとに別の呼び出しとし、入力は `03_plot.json` と `05_draft.md` とする。
- 結果は `06_check/<項目>.json` に保存し、`06_check_report.md` にまとめる。
- 検査結果に基づく自動再生成は行わない。
