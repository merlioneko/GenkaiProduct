## 推奨する進め方

既存のファイル中心の構成を維持し、問題ごとに小さな変更へ分ける。失敗処理を先に直し、操作の仕様を整えてから、品質評価へ進む。モデル変更や自動修復を最初の対策にしない。

| 順序 | 対象 | 推奨案 | 性質 |
|---|---|---|---|
| A | Checkの結果欠落、退避前検証 | 必須項目を厳密化し、入力・設定を検証してから退避 | 既存仕様に沿う修正 |
| B | 失敗診断、古い案内 | 終了理由・検証結果を分け、確定済み仕様に案内を合わせる | 既存仕様に沿う改善 |
| C | 明示指定がない入力 | 見出しを必須にしたまま空の指定リストを認める | 入力仕様の明文化が必要 |
| D | 手編集後の再結合 | LLMを呼ばない `assemble --run` を追加 | CLI・退避・評価票の仕様判断が必要 |
| E | 生成設定の履歴 | 初期設定を保持し、操作単位で設定・成果物を対応付ける | 履歴の仕様判断が必要 |
| F | Concept照合、physicalの誤検出 | 固定資料で性能を測り、その結果を受けて改善 | 評価計画・人手判断が必要 |

通常CLIの実ロード長の確認は後続候補とする。速度短縮と `run` へのCheck統合はD50・D53どおり別途判断し、今回の不具合修正には含めない。

## A-1. 不完全なCheck応答を成功にしない

**変更案**: [schema.py](../novel/schema.py)の `CheckResult.issues` から既定値を外す。`item` と `issues` の両方を必須にする。`issues: []` は正常な「指摘なし」、省略・null・配列以外は形式エラーとする。機械検査の返却箇所も明示的にissuesを渡す。

[check.py](../novel/phases/check.py)の既存の形式エラー処理を利用し、生出力・エラー種別・既存の部分結果を保存して停止する。後続項目は未実行とし、省略項目の補完や再試行はしない。保存済みの正常な検査JSONはそのまま読める。

**確認案**: 実SDKへのメモリHTTP応答で、各LLM項目のissues省略・null・不正型を投入する。正常な空配列との違い、非ゼロ終了、生出力保存、後続未実行、本文・07の不変を確認する。既存の引用不一致・30字超過テストも維持する。JSON Schemaのrequiredにもissuesが入ることを確認する。

変更対象: schema.py、必要な呼び出し箇所、[test_check.py](../test/test_check.py)・[test_schema.py](../test/test_schema.py)。関連: SPEC「Check」、AC-M6-3、D24・D52。ローカルGemmaでの1回の正常応答確認はスキーマ互換性の確認として行い、検出精度の再評価とは区別する。

## A-2. 入力・設定を検証してから退避する

**変更案**: Concept/StructureのCLI経路を「読み込みと検証 → 退避 → 設定記録 → 生成・保存」に揃える。読み込みと検証はファイル更新・モデル切替・API呼び出しを行わない。

| 操作 | 退避前に確認するもの |
|---|---|
| Concept再実行 | 00の読み取り・空でないこと、concept設定、思考設定、生成・照合の両プロンプト |
| Structure | Conceptの読み取り・パース、structure設定、思考設定、プロンプト |
| Writing／write | 現在のPlot・再開位置・先行シーン・思考設定の検証に、執筆プロンプトの読み取りを加える |
| 新規run | 全担当設定と利用プロンプトを開始前に確認。まだ生成されていない中間成果物は生成後に検証 |

実装では各フェーズ内に小さな準備関数を置き、読んだ入力・プロンプト・設定を実行側へ渡して再利用する。検証直後に同じファイルを無条件で読み直す構造を避ける。データスキーマへI/Oを移したり、Stage基底クラスを導入したりしない(D30・D36)。

**失敗の扱い**: 事前検証の失敗では01〜07と既存アーカイブを変更しない。生成開始後のAPI失敗では、従来どおり旧成果物を退避先へ残し、生成済みの新成果物を保持して停止する。API失敗まで含めた全操作の自動巻き戻しは本案の保証に含めない。

**確認案**: 壊れた／欠落したConcept、空の00、担当設定欠落、思考設定不正、プロンプト欠落について、失敗前後の成果物ハッシュ・アーカイブ一覧の一致とAPI呼び出し0件を検証する。成功時の退避範囲、生成途中失敗時の保存も確認する。

変更対象: [main.py](../main.py)、Concept/Structure/Writingのフェーズ関数、[test_stage.py](../test/test_stage.py)・[test_writing.py](../test/test_writing.py)・[test_pipeline.py](../test/test_pipeline.py)。関連: D21〜D24、AC-M2-4・AC-M4-6。

## B. 失敗診断と案内を整える

### ログ

[gateway.py](../util/gateway.py)の1呼び出し1記録を維持し、応答の `finish_reason` と安全な分類コードを追加する。分類例は `no_choices`、`non_stop_finish`、`empty_content`、`schema_invalid`。応答がないときの終了理由・usageはnullとする。APIエラー本文・ヘッダ・鍵は記録しない。

既存callsのsuccessは「gatewayの応答・スキーマ検証まで成功」の意味を維持する。引用照合まで成功した意味へ後から変更しない。Checkのmetadataへ項目別の `pending/running/success/error` と失敗段階を保存し、報告書でも同じ状態を使う。gatewayの呼び出しIDを返し、項目結果・error.jsonとcallsを対応付ける。項目照合の失敗を追加のAPI呼び出しとして二重計上しない。

**確認案**: 長さ制限終了、空応答、通信失敗、スキーマ違反、引用不一致を区別できること。引用不一致ではgateway成功・項目検証失敗の関係が明確なこと。1呼び出し1行、秘密の非記録、旧ログを読む比較スクリプトの互換性を確認する。旧ログの欠けた終了理由は補完しない。

### 案内

[evaluation.py](../novel/evaluation.py)の新規評価票をD51確定後の表現へ更新し、「合否案」を「合否」にする。基準の内容・閾値は変えない。SPECの設定例をD37・D53と一致するGemma/nullに直す。MILESTONESの過去時点の記述には、その時点の日付が分かる注記を添える。保存済みの評価票・検証記録の内容は保持する。

**確認案**: 新規テンプレートの基準表示と既存評価票の非上書き、SPECと設定例の一致、文書リンク・差分の確認。過去の実機結果の再検証とは扱わない。

## C. 明示指定のないリストを空で表現する

**推奨する仕様案**: `# 制約`・`# 出来事`・`# 構想` の見出しと順序は必須とし、制約・出来事はそれぞれ0件以上を認める。指定がなければ見出しの次を空にする。「なし」を指定要素に追加したり、補完した出来事を指定要素へ格上げしたりしない。原入力と構想本文は空を認めない。項目がある場合の空文字・不正な箇条書き・番号飛びは従来どおり拒否する。

例: 「雪の町を舞台にした静かな短編」なら、舞台・雰囲気は制約、出来事は空とする。補完した展開は構想本文とPlotのbeatsへ置く。

後段も合わせる。Structureはconstraints/eventsをそのまま転記し、eventsが空なら各scene.coversを空配列にする。beats・登場人物・設定・シーンの既存の最低件数は維持する。Plot機械検査ではevents空/covers空を正常とし、存在しない番号は引き続き報告する。WritingとCheckは空リストを扱い、指定出来事がないことを生成不備とみなさない。人手評価票には指定リストが空であることと、原入力を確認する必要があることを表示する。

**確認案**: 制約のみ、出来事のみ、両方空の形式往復、見出し欠落との区別、空項目拒否、events空でStructure→Writing→Checkが動くスタブ試験。既存の具体・曖昧入力も回帰確認する。ローカル試験では舞台・雰囲気だけの入力を追加し、指定の捏造がないか人手照合する。パーサの成功だけでは要素保持の成功としない。

変更対象: [concept.py](../novel/phases/concept.py)、Concept/照合/Structure/Checkの関連プロンプト、必要に応じ評価票、各テスト。SPEC「02_concept.md」「Structure」「指定要素」を先に明文化する。AC-M2-2等の既存の具体入力条件は緩和しない。

**代替案**: 出来事・制約を必ず含む入力だけに制限する方法もあるが、曖昧なアイデアからの生成という用途を狭めるため推奨しない。

## D. 手編集後の明示的な再結合を追加する

**推奨する操作案**:

```powershell
python main.py assemble --run creations/<run-directory>
python main.py stage check --run creations/<run-directory>
```

`assemble` はAPI・バックエンド設定を必要としない補助操作とする。既存Writingの自動Assembleは維持する。

1. 00・Plot・全シーンを読み、シーンの欠落・余分・空本文・番号不正を検証する。ここまでは退避しない。
2. 読み取った同一の本文から新しい草稿と未評価の評価票を準備する。結合規則・字数集計を既存のWriting/Checkと共有する。
3. 旧05・06・07を同じアーカイブへ退避し、05と未評価の07を保存する。00〜04・01の生成設定は書き換えない。
4. 保存時には一時ファイルからの置換を使う。途中失敗時はエラーで止め、退避先と保存済みファイルを示す。複数ファイル全体の完全なトランザクションは約束しない。

**古い評価の扱いの推奨**: 明示的なassembleは新しい評価開始とし、草稿が同じでも06・07を退避する。本文の一致だけでは、手編集したPlotと古い評価の対応を判断できないため。この操作を繰り返すと評価票が未評価へ戻ることをヘルプに明記する。将来、全依存ファイルの対応が確実になった段階で「全入力が同一なら何もしない」を検討できる。

中間シーンの変更で後続の内容も変わる場合は、B'方式に従って `write --from <次のシーン>` で後続を再生成する。assembleは保存済み本文を結合するだけで、文脈上の整合性を保証しない。草稿05だけを編集した場合は、正本である04へ変更を移してから実行する。旧05は退避で保護する。

実装は「全シーンの検証・読み取り」「草稿の組み立て」「保存・字数表示」を共有し、CLI側で退避・評価票生成を管理する。既存run/write内のAssembleが二重退避しないよう、内部関数と明示的CLI操作を分ける。

**確認案**: 最終シーンの手編集→assemble→Checkをスタブで通す。04の全ファイルがバイト単位で不変、旧05/06/07が保存、新07が未評価、API呼び出し0件を確認する。壊れたPlot・不足/余分/空シーンで退避前に止まること、設定ファイルがなくても動くこと、通常run/writeの退避範囲が変わらないことも確認する。

変更対象: main.py、run.py、context.py、writing.py、check.py、evaluation.py、CLI/退避/結合テストとtest/README。SPECのCLI・Assemble・退避・評価票へ動作を追加する。Checkが草稿を黙って更新する案と、`write --from N+1` を結合の別名にする案は、操作の意味が分かりにくいため採用しない。

## E. 操作ごとの履歴で生成条件を追えるようにする

**推奨する仕様案**: 新規runの `01_config.json` は実行開始時の設定として保持し、stage/writeによる上書きをやめる。新しい操作の条件は `_history/<operation-id>/` に保存する。01だけを現在の全成果物の生成条件と解釈しないよう、評価票の案内も更新する。

| 記録 | 内容案 |
|---|---|
| `start.json` | schema_version、操作ID、開始時刻、操作名・再開位置、公開設定、入力・利用プロンプト・関連コードのハッシュ |
| `result.json` | 終了状態、終了時刻、退避先、生成済み成果物の相対パスとハッシュ、途中失敗の段階・安全な分類コード |
| callsへの追加 | 操作IDと呼び出しID。既存フィールドの意味を維持し、既存集計との互換性を保つ |

準備・検証が通った後、退避より前にstartを保存する。startを保存できなければ退避しない。正常終了だけでなくAPI失敗・通常の中断でもresultを保存し、Writingは途中まで保存できたシーンを記録する。強制終了でresultがない履歴は「完了未確認」とし、成功へ補完しない。履歴は上書きせず、各操作は一意のIDを持つ。

公開設定はAPIキーを除外し、接続先URLに認証情報が含まれる場合は除去する。任意の思考用リクエスト本文は秘密を含み得るため丸ごと保存せず、公開可能と定義した項目と指紋を記録する。設定上のcontext_lengthと観測していない実ロード長を混同しない。

**途中再開と手編集**: `write --from 3` なら先行シーン1・2も入力ハッシュへ記録し、新規シーン3以降を出力として記録する。前回の出力ハッシュと一致しないファイルは「外部変更または来歴不明」と扱い、過去のLLM生成条件をそのまま帰属させない。最新の一致する出力記録から成果物ごとの操作をたどれるようにする。外部編集の作者・時刻・途中履歴まで復元できるとは扱わない。

**旧runとの互換性**: 既存01は初期設定とは断定できない。初回の更新時に現存01と現存成果物の指紋を移行記録として保管し、「導入時に存在した設定・元の生成条件は未記録」と明示する。旧アーカイブとcallsは保持し、推測で履歴を埋めない。履歴がない旧runも引き続き読み込める。

Checkは生成用01を更新せず、06のmetadataを保持しつつ操作IDで履歴へ結び付ける。assembleはモデル設定なしの操作として記録する。baselineも同じ記録形式を利用できるが、既存の出力ファイル名は変えない。M5/M6の固定済みstudyへ履歴を後付けしない。

**確認案**: モデルAでConcept→設定BでStructure、途中から設定CでWritingを行い、各成果物と対応する設定が追えること。手編集、途中失敗、同秒の再実行、旧run、秘密の非記録を確認する。履歴保存の失敗で既存成果物を退避しないことも試す。比較スクリプトの既存テストで集計互換性を確認する。

変更対象: run.pyまたは小さな履歴専用モジュール、main.py、gateway/log、各フェーズの呼び出しID受け渡し、評価票・関連テスト。スキーマへI/Oを持ち込まず、一般的なワークフローエンジンには広げない。SPECの01・履歴・callsの役割を更新する。単に旧01を退避する案では、残した上流成果物・途中再開・手編集の対応まで解けないため、操作単位の記録を推奨する。

## F. 検出性能を測ってからプロンプトを改善する

### Concept照合(U13)

最初は現行のQwenと照合プロンプトを固定して測る。原入力とConceptを組にし、欠落・順序変更・意味の弱化・主体/受け手の逆転について、異常例と正常な言い換えの対を用意する。指定リストは正しいが構想本文だけ誤る例も含める。出典の確認できる既知例と合成例を分ける。

初回規模の案は4分類それぞれ正常/異常の計8組、各2回の16呼び出し。件数は着手時に確定する計画案であり、性能保証の基準ではない。正解・許容範囲を試験前に人手で固定し、真陽性・誤検出・見逃し・失敗・時間を記録する。同じ原因の指摘を重複加算しない。

見逃しが再現した分類についてのみ、主体・動作・受け手と「指定リスト／構想本文」の両方を照合するようプロンプトを調整する。修正に使った資料と別の評価資料を分ける。別モデル採用はその後の比較候補とし、初めからスキーマを拡張しない(D40)。結果を確認してU13の未解決部分を明記する。原入力との人手照合は継続する。

### physicalの誤検出とCheckの一般性

膝の動作を一律の不可能例として挙げる文言を除く案を、旧版と比較する。「膝なら常に許可」とする除外規則は追加しない。明確な破綻・設定上許される能力・コメディ上の誇張を対比し、両立しない事実を根拠にする指示へ整理する。

M6の5資料は固定した回帰資料として保持し、R02の既存の人手判断も引き継ぐ。別作品の正常例・明確な破綻・許容する誇張を追加し、プロンプト調整用と最終確認用を分ける。まずGemmaの旧/新プロンプトを同条件・同じ資料で比べ、同じ資料で複数回採取してばらつきを見る。旧M6の実測を新条件の対照群へそのまま流用しない。

採否は既知の見逃し、誤検出、新規の妥当な指摘、実行失敗、所要時間を並べて人手判断する。自動的な精度閾値は新設しない。既知例だけで改善しても一般精度向上とは断定しない。品質試験はローカルのみ(D1・D2)とし、新しい計画・プロンプト・資料・条件を固定して記録する。

変更候補: 比較用スクリプトと出典付き資料、Concept照合・physicalプロンプト。採用結果と未検証部分はMILESTONES、判断が確定した場合だけSPECへ反映する。

## 通常CLIの実ロード長はどう扱うか

直近はtest/READMEの手動設定と既存の超過時停止を維持する。改善する場合は、設定値・観測した実ロード長・観測時点を区別して表示する方式を推奨する。既にロード済みなら呼び出し前、JITロードならロード後に観測する。ただし生成後に不一致を知るだけでは事前保護にならない。

実ロード長を毎回強制するには明示ロード方式・既存モデルの再ロード・追加時間の仕様判断が必要になる。入力のトークン数に加えて生成量・思考量も変動するため、長さの確認だけでコンテキスト超過を防げるとはしない。B'方式と自動切り詰め禁止は維持する。必要性が見えてから別の改善計画にする。

## 実装と検証の区切り

1. A-1、A-2、Bを別の変更単位で実装し、失敗経路と既存の成功経路をオフライン確認する。
2. C・D・Eの推奨動作を判断し、採用部分の仕様をSPECへ記録する。既存ACへの影響と必要な追加条件をそこで確定する。
3. C、D、Eを順に実装する。Dは履歴導入前でも動作でき、Eで操作記録を追加する。
4. スキーマ変更と空指定入力のローカル動作確認を行う。元の評価資料を上書きせず、変更後の版・条件を記録する。
5. Fの正解資料と評価計画を確定して採取する。プロンプト変更の採用とU13の結論は結果を見て判断する。

テストは各変更に対応する既存unittestへ追加し、変更単位で関連テスト、その区切りで全体テストを実行する。過去の138件成功を変更後の成功扱いにしない。保存物には検証日・対象コミット・環境・コマンド・結果・未検証範囲を残す。文書だけの変更ではアプリテストを再実行せず、リンクと `git diff --check` を確認する。

## 実装前に判断する仕様案

| 判断対象 | 推奨する選択 | 理由・注意点 |
|---|---|---|
| 指定なしの入力 | 見出し必須、制約・出来事の空リストを許可 | 補完した内容をユーザの指定と混同しない |
| 再結合の操作 | 独立したassembleコマンド | モデルを呼ぶ操作と再結合を区別できる |
| 再結合時の評価 | 毎回旧05/06/07を退避し、新07は未評価 | 古いPlotや本文への評価を誤って再利用しない。無変更の繰り返しでも評価票が更新される |
| 生成条件の履歴 | 新規01は初期設定、操作履歴を追加 | 上流成果物と再開後の本文が別条件でも追える。既存runの過去条件は復元不可 |
| 品質改善の開始点 | U13の現行性能測定とphysicalの旧新版比較 | 変更の効果を観測でき、既存の採用判断を根拠なく覆さない |
